## 为可迁移性作出的取舍

- 先由 Agent 结合代码起草事实和建议，仅对影响范围、业务正确性、风险或授权的缺口提问；不用每一步都等确认。
- 分发版统一 P0=本次必须验收、P1=后续重要、P2=可选；不用源文不同编号惯例混写。
- 研发阶段以测试前置为目标；没有记录红灯就不补写“严格 TDD 已执行”。
- 原 CODE/BIZ/ENV/AI 失败分类把 AI 改为 TEST，描述问题本身，不按作者归因。
- 原资料中的固定文档数量、Skill 数量、代码占比、Agent 数量、等待时长、成熟度分数与提效倍数不作为成功标准。保留真正影响交付的决策和验证。
- 不复制私人服务器/路径/账号、特定厂商地址、个人审批人；连接、密钥和技术栈在业务项目配置。
- 不无条件要求所有项目使用数据库、软删除、熔断、微服务或 Allure；没有适用场景时写 N/A 与原因。
- 保留“人工复核”的责任，不假定签名文件能认证身份。源码指纹只用于失效检查，不冒充防篡改系统。
- 工具的章节检查只能发现缺失/占位，不能判断内容实质正确。由阶段内容审查、独立验收条件和可失败的行为测试承担后半部分。

## 本版的落地检验

[任务清单实例](../examples/task-list/README.md) 给出完整材料和真实 SQLite/CLI 实现。工具测试在临时目录初始化 M 档、加载材料、执行测试/编译；再改坏“完成任务”行为验证红灯。审批始终保持 pending，没有把教学示例的成功伪装成真实业务验收。

这些检验支持“可以启动并指导新项目”的结论，不支持“已经证明所有项目效率提高”。真实效果仍按 [维护与迁移](maintenance.md) 的两个项目试跑记录评估。
