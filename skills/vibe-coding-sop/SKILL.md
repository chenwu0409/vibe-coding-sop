# Vibe Coding SOP

If `.sop/project.json` exists, read it and the project's agent entry file; run the read-only `python .sop/runtime/sop.py guard` before coding, confirm the project has a local Git baseline, and treat its output as the task's starting baseline. Use `check` or `audit` for the detailed gate named by guard. For full-stack or platform work, run the applicable `doctor` profile before implementation. Load `.sop/core/workflow.md` and only the documents relevant to the current task.

If initialization is requested, locate the distributed package containing `sop.py` and `profiles/`. Read its README and initialize the specified project with a suitable profile. If the package is unavailable, report that dependency rather than inventing an installation command.

Follow the workflow's stage routing into .sop/core/stages: each guide supplies steps, examples, completion criteria, and failure handling. Draft project-specific documents from observed code and user goals; ask only about material uncertainty or authority. Do not ask the user to fill every template before making progress. For a filled worked example, read .sop/runtime/examples/task-list/README.md.

For projects targeting a platform runtime (mini-program, browser, mobile, desktop, plugin, game engine, or similar), identify the platform configuration, actual source root, scan/package rules, reserved names, and real compile/package entry during design (write it in design.md for M/L or plan.md for S). Create `.sop/platform-flows.json` from the platform route/config and requirements: inventory pages, select required critical user flows, and record steps and evidence. Execute compilation and every required flow on the real platform when the tool is available. For WeChat mini-programs, load the compiler and automator skills, and load debugger/previewer when applicable. If unavailable, record the exact ENV blocker, owner, next action, and mark the flow unverified; Node/Python tests, syntax checks, mocks, or a successful compile alone do not establish platform flow coverage.

Convert the change into observable acceptance conditions. In tasks v2, make the current release's required task/AC scope explicit; backlog work does not belong in that scope. Link each critical AC to a test or manual validation and work in small vertical slices. After every task, update the ledger and affected documents, run `sync`, review and commit the diff with the task ID, then run `checkpoint --task <ID>`. A required task is not done until its tests/evidence exist and verification is passed. Record actual human decisions and their source; never infer approval from a generated template.

Advance task state through `python .sop/runtime/sop.py task start|block|verify|done <TASK-ID>` rather than writing a completion state directly. `task verify` checks that declared test and evidence paths exist; `task done` requires that verification has passed. Use `task block` with `--reason`, `--owner`, and `--next-action` when evidence is unavailable.

Before `checkpoint --stage L3`, require at least one done/passed task, a fresh successful `verify` report for the current source/configuration, a passing `audit --stage L3`, and a clean Git worktree. A platform or environment blocker remains explicitly blocked/unverified; it is not converted into an implementation-complete claim.

Before closing L3/L4 work, run `python .sop/runtime/sop.py audit --stage <stage>` to catch missing ACs or declared code/test paths and, when enabled, incomplete platform verification records. Audit is a consistency check, not a test or approval.

When requirements, acceptance conditions, constitution, design, plan, platform boundary, project configuration, shared contract, source, or task status changes, rerun `check` immediately; the sync record also becomes stale until `sync` is run after the affected materials are updated. The tool's `scope_sha256` is the freshness boundary: affected approvals are stale until the real reviewer re-confirms the new scope. Independent exploration may continue while approval is pending, but dependent implementation is not delivery-ready. For UI, gestures, defaults, and other interaction semantics, record the behavior in AC/design and add a real manual or platform-level check; pure logic tests cover only the logic seam.

Reassess risk whenever the task touches health, financial, identity, child, or location data; permissions; cloud sync or external APIs; notifications/payments/bulk deletion; irreversible migrations; or real-user release. Local-only storage is not by itself a reason to mark sensitive data normal. Before delivery, synchronize plan/development/validation with the current source, advance `state.json.target_stage` to L4, preserve a local Git recovery baseline, and complete handover.md.

Inspect configured commands before `verify`. Use its `SOP_RUN_ID` for isolated test data and require cleanup to remove only that run's data; inspect the redacted logs and lifecycle result. For platform work, preserve real compile/smoke evidence and run `attest-platform`; do not edit passed manually. For delivery, update the environment matrix and tasks, run `audit --stage L4`, `sync`, commit governance records, register `checkpoint --stage L4`, then run `check --stage L4`. Read `.sop/runtime/docs/protocol.md` for the exact interfaces and ordering. Report every blocker and unverified item; never fabricate test counts, evidence, environment status, or approvals.
