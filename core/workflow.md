# 按变更推进的 L0–L4

先读项目 `.sop/project.json`，运行 `check`。根据现有代码和本次目标确定缺失的决策，复用仍然有效的材料。每个功能以一个可演示的纵向切片推进，阶段可迭代回退。

| 阶段 | 输入与动作 | 完成证据 | 失败回到 |
|---|---|---|---|
| L0 约束 | 目标、现有系统；明确技术约束、不做什么、授权范围 | constitution 完整，所需复核已登记 | 澄清约束 |
| L1 对齐 | 需求、用户场景；消除影响验收的歧义 | requirements 有可观察结果；按需 glossary/wireframe | 业务决策 |
| L2 设计 | 已确认需求；确定模块边界、接口、异常和数据变化 | design（适用时）、risk（高风险）及设计复核 | L1 或设计探索 |
| L3 计划 | 已选设计；划分小步任务和验证命令 | plan；tasks 写依赖和文件所有权；regression 写受影响路径 | L2 |
| L4 验证 | 实现、测试、回归与真实使用场景 | 新鲜自动检查证据、人工验收记录、交接文件 | 按根因回退 |

## 触发原则

- 澄清：只追问会改变范围、实现或验收的问题。需求字数不决定是否追问；合理假设记入计划。
- 领域建模：多个名称指向同一概念、跨模块概念冲突时维护 glossary，记录代码对应名称。
- 模块设计：让接口隐藏复杂度；用调用方是否容易使用评估，不按固定方法数量拆模块。
- TDD：确定行为的业务逻辑及 bug 修复，先观察失败再实现；探索性 UI、原型可先实验，合入前补适当验证并记录原因。
- 接口委托：先决定共享契约、数据迁移和外部依赖，内部实现和重复劳动交给 Agent。
- 上下文维护：只沉淀可复用约束和经验；出错先定位根因，避免无限追加规则。

## 自主执行和复核

已获授权的实现、局部测试和可逆修复连续推进。尚未授权的范围变化、关键业务歧义或发布操作才请求相应决策。人工复核可复用用户已有明确意见并记录来源，Agent 不能代签。

自动测试失败时保留日志并区分 CODE / BIZ / ENV / TEST。CODE 修实现；BIZ 请求业务决策；ENV 排查前置条件；TEST 用独立需求证据判断测试是否错误，不为绿灯降低断言。连续两次同因失败无新证据时暂停重复尝试，报告根因假设和所需信息。

回归范围来自接口调用者、数据读写方和关键用户路径。覆盖率是辅助信号。上线前按风险验证发布与回滚，发布仍需要本次任务的授权。

## 完成与反馈

交付附实际命令、结果、未验证项与下一步；人工验收检查真实场景。复盘记录耗时、返工、逃逸缺陷、人工介入次数，据实际成本调整档位。低频交互和少写代码仅是手段，不代替质量与效率。
