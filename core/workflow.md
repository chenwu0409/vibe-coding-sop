# Vibe Coding 执行总纲

目标是以可控的返工成本交付可验收的功能。当前版本面向单 Agent、单工作区、单一事实源；不把并行 Agent、分支合并和跨 Agent 交接作为已支持能力。每次任务先明确“这次改变什么、如何证明、哪些原行为必须保留”，再选择所需材料。

## 第一次接入

1. 阅读项目已有 README、依赖清单、目录、测试、Git 状态；区分新建项目和存量系统。已有的有效决策可直接引用。
2. 选择档位：S 适合边界清晰的小工具/局部改动；M 适合需要明确接口和数据的业务应用；L 增加跨模块术语、任务拆分和独立回归文档，仍由单 Agent 在单工作区执行。风险与体量分开，敏感数据/权限/不可逆变更按实际影响评估 high。
3. 初始化后按下表读取手册。Agent 负责从用户信息和代码证据起草文档，只把影响业务结果、授权或高成本返工的未知项交给负责人。
4. 配置真实 test/build/lint/security 命令，初始化项目自己的本地 Git 并建立命名基线提交，先跑现有基线。若目标是小程序、浏览器、移动端、桌面端或其他平台运行时，额外识别源码根目录、平台扫描/打包规则和真实编译入口；环境未就绪单独报告，不能当作实现缺陷，也不能假装通过。
5. 明确一个最小端到端切片，按阶段补齐决策后立即实现和验证，后续切片复用有效材料。若项目包含客户端、API、业务服务和数据库，端到端必须真实穿过这些边界，不能用各层单测拼接成“已联通”。

## 生产级补充门槛

生产级不是“文档更多”，而是证据链闭合。每个项目必须有自己的本地 Git 仓库和命名基线提交；不要求远端服务器，但不得依赖未命名的工作区状态。进入下一阶段时，Agent 必须推进 `.sop/state.json` 的 `target_stage`，完成同步后运行 `sync`；最终交付前必须为 `L4`。计划、开发落点、验证和交接中的状态、测试数量、阻塞和未验证项必须与当前源码一致，旧的“待开始/TODO/未实现”不能留作当前结论。

### 强制同步协议

`.sop/tasks.json` 是任务状态的机器可读权威来源，`.sop/docs/plan.md` 是任务的解释性来源。每项任务必须关联 AC、代码落点、测试、证据、实现状态和验证状态。任务只有同时满足以下条件才能标记 `done`：代码落点已完成、测试已执行、验证证据已记录、`verification` 为 `passed`。平台或人工仍未完成时，任务只能保持 `in_progress`/`blocked`，不能标记 done。

每完成一个任务或阶段，必须按顺序执行：

1. 更新 `.sop/tasks.json`；
2. 更新受影响的 `plan.md`、`development.md`、`validation.md`、`risk.md` 或 `handover.md`；
3. 核对 AC→任务→测试→证据链及真实测试数量；
4. 运行 `python .sop/runtime/sop.py audit --stage <当前阶段>`；
5. 运行 `python .sop/runtime/sop.py sync`；
6. 运行 `python .sop/runtime/sop.py check --stage <当前阶段>`；
7. 建立本地 Git 提交，提交信息包含任务或阶段 ID。

`sync` 会记录当前阶段文档、任务清单、源码和配置的指纹。任何一个发生变化，之前的同步记录立即失效；未重新同步时，`check` 必须失败。同步不是审批，也不能把自动测试通过改写为人工验收通过。

以下任一条件出现时，重新评估 `risk`，必要时切换 high 档并补风险/安全/发布复核：健康、财务、身份、儿童、位置等敏感数据；登录/权限；云同步或外部 API；通知、支付、批量删除等外部副作用；不可逆迁移或面向真实用户发布。只写“本地存储”不能自动把敏感数据降为 normal。

目标平台项目的 build 至少包含三层检查：平台配置 schema/字段有效性、源码边界/保留规则、真实平台编译或导入。真实编译不可用时，必须保留具体 ENV 阻塞和人工复跑步骤；本地语法检查不能代替它。UI/触摸/手势还要有平台冒烟步骤。

Full-stack 项目再增加四层检查：API 契约校验、空库迁移/初始化、真实数据库集成、跨客户端端到端。`test`、`build`、`security` 只能证明配置的命令，不自动证明各组件已联通；必须在 environments.md 和 validation.md 中记录组件、环境、数据库和实际证据。

交付前应有可恢复基线：优先 Git 提交或明确的压缩包/目录快照、版本和恢复步骤。没有版本控制时要说明限制，不能把“工作区当前状态”称作可回退版本。`handover.md` 必须填完，包含接手者复跑命令、真实平台步骤、未验证项、恢复边界和责任人。

## 每次任务的强制闭环

这是 Agent 每次接到新任务、继续被中断任务或收到新反馈时都要执行的固定顺序。它不是建议清单；缺少某一步时，只能报告“未就绪”，不能把代码已修改当作任务已完成。

1. **起始门**：先读 AGENTS.md、`.sop/project.json`、`state.json`、当前阶段材料和工作区差异；然后运行 `python .sop/runtime/sop.py check`（需要时指定 `--stage`）。保存检查结果，明确当前阻塞、基线和本次目标。若是目标平台项目，先确认平台配置、源码根目录和真实编译入口。
2. **变更门**：需求、验收条件、宪法、设计、计划、平台边界、项目配置或共享契约发生变化后，立即重新运行 `check`。范围哈希变化导致的需求/设计/验收/发布复核必须标记为过期；共享契约或业务语义未重新确认前，不把依赖它的实现宣称为完成。可以继续做独立探索，但要明确处于“复核待完成”状态。
3. **切片门**：每个纵向切片先有一个可观察 AC 和对应测试/人工验收；确定行为的逻辑或 bug 遵循 red→green→refactor。UI、手势和平台行为不能只用纯函数测试代替，必须另列真实界面操作或平台导入/编译检查。
4. **交付门**：代码稳定后按 `test/build/lint/security` 配置运行 `verify`，审阅真实日志、收集数量和跳过项，更新 `validation.md`；目标平台再执行真实编译/打包/导入检查。先运行 `audit --stage L4`，再同步任务和文档，建立 Git 提交，最后必须再次运行 `check --stage L4`，逐项处理阻塞。只要 L4 未就绪、平台检查未验证或人工验收待完成，就只能交付为“部分完成/待验证”，不能写“已完成”。
5. **交接门**：填写 `handover.md`，同步任务和文档，区分已实现、已验证、未验证、阻塞和责任人；Git 基线、同步记录和快照生成不等于交付通过。接手者必须重新读取材料并按当前环境复跑受影响检查。

这五道门的完成证据分别是：起始 `check` 输出、变更后新的 scope/复核记录、AC→TC 或人工步骤、`verify` 与最终 L4 输出、handover 快照。任何证据来自旧范围或旧源码，都不算本次任务证据。

## 何时读什么

下列链接位于分发包的 core 下；初始化后同样可在 .sop/core 下使用。

| 当前任务 | 必读手册 | 项目产物（.sop/docs） | 离开阶段的条件 |
|---|---|---|---|
| L0 建立边界 | [项目约束](stages/00-constitution.md) | constitution.md | 稳定约束、理由、权限边界可判断 |
| L1 澄清需求/原型 | [需求与调研](stages/01-discovery.md) | requirements.md；按需 research/glossary/wireframe | 本次核心故事有正常与失败验收，阻塞问题已决策 |
| L2 设计 | [技术设计](stages/02-design.md) | design.md；high 加 risk.md | 接口、数据、不变量、失败行为、平台边界和验证方法明确 |
| L3 准备实现 | [计划与开发](stages/03-planning.md) | plan.md；M/L 加 development.md；按需 tasks/regression | 首个 Quickstart 可执行，宪法对照无未处理冲突 |
| L4 编码 | [编码反馈](stages/04-implementation.md) | 代码、测试、计划进度、`.sop/tasks.json` | 小步验证、新行为与既有行为同时成立；任务状态已同步 |
| L4 验证交付 | [测试与质量门](stages/05-validation.md) | validation.md、`.sop/tasks.json`、执行证据、真实复核 | 验收映射完整，自动测试与目标平台验证有证据，未验证项明示，状态已同步 |
| 交接/发版 | [发布与交接](stages/06-delivery.md) | handover.md、交接快照 | 接手者能复跑并理解为何这样改 |

## 材料与行为

- 文档写项目事实、决定、待决事项和可执行检查；模板中的示例只帮助理解，不能作为本项目的完成证据。
- S 可在 plan 中合并接口与代码落点，但必须保留适用的决策。没有数据库写“无持久化及迁移，因为……”，而不是发明一套表。
- 已有项目只更新受影响内容。小修复先复现，再定位最小影响面、回归验证；不为每个 bug 重写项目宪法。
- 多角色可以由同一人承担。已有明确授权和决定无需反复确认；负责人审批业务取舍、共享契约的重要变化和交付，Agent 连续执行已授权任务。
- 首版的 research、原型、技术设计、DD、Plan 分工在阶段手册明确。单一事实引用权威文件，如 API 字段引用契约、DDL 引用迁移文件。
- check 是材料/登记证据检查，不理解业务语义。Agent 与负责人仍须按各手册的内容审查问题逐条核对。

## 状态与回退

state.json 的 target_stage 是本次要检查的阶段，不是自动批准。check 累积验证此前阶段。自动证据失效后重跑，人工复核范围变化后重新确认受影响部分。

| 发现的问题 | 回退位置 | 要修正的内容 |
|---|---|---|
| 无法判断用户到底接受哪种结果 | L1 | 验收标准及业务决定 |
| 接口把内部细节推给调用者 | L2 | 边界与契约 |
| 任务状态与文档不一致 | L3/L4 | 更新 tasks/plan/development/validation，运行 sync 后再继续 |
| 工作区无可恢复基线 | L0/L3 | 初始化本地 Git，建立命名提交 |
| 实现不满足已确认规则 | L4 | 最小代码修复及回归 |
| 新功能正确但旧路径坏了 | L3/L4 | 影响面、基线测试和实现 |
| 环境、账号或依赖不可用 | 当前阶段的前置条件 | 证据、替代验证及仍未验证项 |

每次交付记录耗时、返工、逃逸缺陷和人工介入，持续裁剪没有帮助决策或验证的文档。当前版本不提供多 Agent 并行、自动合并或自动发版能力。工具不执行自动升级或自动发版。
