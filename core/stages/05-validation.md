# L4：测试、质量门和验收

输入：AC、实现、影响面、项目测试环境。输出：validation.md 和原始执行证据。对应测试验证体系、用例/报告模板、TC 映射及 Quality Gates（含回归门）。

## 用例先于结论

每条关键用例具备五要素：唯一 TC 编号、业务目的、前置条件、输入、可断言的预期输出。按适用性覆盖返回值、存储变化、副作用和错误；无数据库的纯函数不必伪造 DB 断言。

从每个 P0 AC 推导：正常等价类、边界内/外、异常输入、依赖故障。写入/状态操作再看幂等、事务、资源释放、并发和数据污染。不同用例可以覆盖不同维度，不要求每条用例把全部维度塞满。

AAA：Arrange 准备固定数据/时间/外部响应，Act 调用公开行为，Assert 验证业务结果与不应发生的副作用。纯逻辑用单元测试，数据/协议边界用集成测试，关键用户旅程用端到端或人工真实操作。比例服从风险，不强制 60/30/10。

Full-stack 项目必须明确四类证据：单元行为、API 契约、真实数据库集成、跨客户端端到端。客户端和后端各自的 Mock/单测不能替代真实 API 或真实数据库；数据库测试必须使用隔离的测试库或临时数据库。`verify` 注入的 `SOP_RUN_ID` 是测试数据生命周期标识，setup/测试/cleanup 使用同一值；cleanup 只删除本次 run 的数据，不能用时间范围或“最近记录”代替。

## 需求到执行的映射

validation 中维护 AC → TC → 测试文件::函数/脚本步骤 → 命令/日志：
- 每个本次 P0 AC 都有自动用例或明确的人工验收；
- 每个登记自动用例能被框架发现并执行；文件存在不等于用例被运行；
- 跳过、预期失败和零测试单列，不计为通过；
- 新增实现相关的测试能追溯到行为；框架测试等可以说明“基础设施”来源；
- P0 测试的预期先依据需求审查，避免实现与测试一起写错。

现有工具不解析所有测试框架的 TC ID；Agent/负责人核对映射，项目需要时把框架收集命令接入 CI。不得声称本工具已经完成自动双向映射。

## 验证顺序

1. 检查测试环境隔离、可重置数据、mock 与真实服务边界。
2. 运行相关用例，读取实际收集数量与失败；再运行影响面回归及配置门禁。
3. 保存原始日志/框架报告。框架支持时输出 JUnit XML 供 CI 解析；人读摘要直接用 validation，Allure 仅在需要时启用。
4. 记录环境、源码版本/指纹、命令、用例数（通过/失败/跳过）、覆盖率测量范围。没有测量写“未测”，不能填估计值。
5. 按下表对失败分类，修复后关联旧/新日志。最终用户验收检查真实场景，不能只看 CI 绿灯。
6. 更新 validation 后运行 `verify`，审阅 run ID、脱敏日志和 cleanup；再执行目标平台编译/冒烟，并逐条执行 `.sop/platform-flows.json` 的 required 流程，最后运行 `attest-platform`。全栈项目更新交付环境逐项结果。随后运行 `audit --stage L4` 和 `sync`，提交治理记录、登记 `checkpoint --stage L4`，最后运行 `check --stage L4`。最终 check 的输出必须纳入交付证据；不能用更早一次 check 代替。

7. 每条 AC 的验证结论先写入 `.sop/tasks.json` 对应任务，再同步 `plan.md`、`development.md`、`validation.md` 和风险/交接材料；运行 `python .sop/runtime/sop.py sync` 后才能继续收口。测试通过但任务清单、验证报告或未验证项未同步时，视为未完成。

## 生产级交付前清单

- `state.json.target_stage` 已推进到 L4；requirements/design/acceptance 的 scope 与当前材料/源码一致。
- `.sop/tasks.json` 的 required task 全部 done/passed，required AC 均被覆盖；任务状态与 plan/validation 一致，最新 `sync` 未过期，每项 required task 和当前 HEAD 均有 Git checkpoint。
- plan/development/validation 中的任务状态、测试数量、构建结果、失败修复和未验证项与当前事实一致，没有遗留的过时结论。
- 敏感数据、权限、外部副作用、不可逆迁移和真实发布已完成风险分档；适用的 high 门禁和发布复核没有被 normal 档绕过。
- 目标平台配置已做字段/schema 检查，源码边界已扫描，真实平台编译/导入/冒烟凭据由 `attest-platform` 绑定证据哈希与 Git 历史；不可用时明确 ENV 阻塞和责任人。
- 全栈项目的交付环境检查逐项 passed；test 通过没有覆盖 local-dev/staging/production 的失败或未运行。
- 存在 Git 基线或命名快照，并能说明恢复步骤和数据限制。
- `handover.md` 已填完，`handover` 快照中的 blockers、handover_complete 和 narrative 哈希已审阅。

## 目标平台验证

当项目有目标平台/运行时编译器时，在自动 test/build 之后执行目标平台验证：

1. 确认开发者工具、官方 CLI 或打包器读取的项目配置和源码根目录与 design.md 一致；检查测试、SOP、缓存和构建产物没有落入平台源码扫描范围。
2. 执行真实平台编译/打包/导入检查，保存工具版本、命令或人工步骤及原始输出；运行 `attest-platform` 生成绑定当前源码/Git/流程清单的记录。平台构建脚本可作为 project.json 的 build 命令，但不能用 Node/Python 语法检查冒充平台编译。
3. 从 app 路由、源码和 requirements 建立 `.sop/platform-flows.json`。页面清单用于防止漏页；required 流程只选择本次交付的高风险/核心路径，不要求穷举所有组合。每条流程写入口、步骤、状态和证据路径。
3. 若平台工具、账号、设备或服务不可用，按 ENV 记录具体阻塞、替代验证和责任人；保留未验证状态，不把自动测试全绿写成完成。
4. 若平台扫描规则导致编译失败，先修复项目边界，再增加最小回归检查，确保规则不会因缓存或 SOP 运行重新生成的目录而失效。

## UI 与手势验证

若 AC 涉及页面、点击、长按、拖动、滚动、日期选择、视觉标记或错误提示，validation 至少列出一条真实操作步骤，并同步到 `platform-flows.json`：环境/页面、输入动作、预期可观察结果、数据副作用和证据位置。纯模型或组件单测可以作为补充，但不能单独关闭该 AC。未能打开目标平台时，把该步骤标为 ENV/未验证，写明替代的逻辑验证和下一位执行者；不要把“代码路径已覆盖”写成“用户操作已通过”。

## 失败分类与动作

| 标签 | 判断依据 | 动作 | 何时请求决定 |
|---|---|---|---|
| CODE | 明确契约与测试一致，实现违反 | 最小修复 + 回归用例 + 重跑 | 同因尝试无新线索或需扩大范围 |
| BIZ | 需求冲突/未决定，无法确定正确结果 | 记录两个可能结果及影响 | 业务负责人选择 |
| ENV | 运行时、数据、账号或外部环境不满足前置 | 修复获授权的测试环境，保留失败 | 缺凭证/权限/外部服务 |
| TEST | 测试前置、断言或 mock 违背独立契约 | 引用依据修正测试再跑 | 预期结果仍需业务决定 |

TEST 对应原文 [AI] 类，但人工写错测试也适用。异常类名或关键词只提供线索，不能自动决定根因。避免靠无限重跑掩盖偶发失败。

## 项目质量门（不是工具已经自动实现的功能清单）

| 门 | 如何检查与保留证据 | 未满足时 |
|---|---|---|
| Q-01 行为正确 | P0 AC 映射、测试收集与执行、真实验收 | 阻止本次交付 |
| Q-02 回归安全 | 直接/间接影响表，原行为基线与改后结果 | 补影响面/回归，不仅测新功能 |
| Q-03 输入与数据边界 | 输入/权限/事务/幂等/默认值对应测试 | 修复适用路径 |
| Q-04 凭证与依赖 | 差异审查、可信扫描、依赖来源与锁文件 | 处理实际泄露/高风险发现 |
| Q-05 可维护与可解释 | 负责人能说明关键接口、业务规则和失败策略；lint/类型/构建 | 阻塞缺陷必修，风格建议记录 |
| Q-06 范围与完整性 | diff 对目标；契约/迁移/配置/文档同步 | 删除无关扩张或补遗漏 |
| Q-07 复核与交付 | 决定出处、未验证项、发布/恢复说明、交接 | 明确条件，不冒充已验收 |
| Q-08 目标平台与源码边界 | 目标平台版本、源码根目录、扫描/打包规则、真实编译/打包结果；或明确 ENV 未验证 | 平台编译未通过或边界不明时阻止交付 |

每个适用门记录通过/失败/未验证及证据。无适用场景写 N/A+理由。安全基本检查适用于所有档；high 增加专门 security 自动命令及发布复核。原文 G1–G17 的合并映射见分发版 docs/source-map.md，避免编号混用。

覆盖率按项目定义核心范围与工具口径，阈值结合风险确认。高覆盖率不证明断言有效。函数长度、复杂度和重复率优先作为审查信号；已有项目硬门禁按其配置执行。

## 内容审查与完成

能够沿每个 AC 找到实际测试或人工记录；每个重要受影响旧路径有证据；目标平台项目能找到真实编译/打包证据或明确 ENV 未验证；所有失败、跳过、未测及风险有解释。validation 不手抄整份日志，以路径引用原始输出。负责人处理业务验收和例外，Agent 可整理真实决定，不代签。
