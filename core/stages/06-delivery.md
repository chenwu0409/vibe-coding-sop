# 发布与上下文交接

输入：需求、设计理由、直接/间接影响、测试/验收证据。输出：handover.md 与机器快照。对应 context-json 协议和 CI/CD 指南。

## 发布前按项目需要检查

- 环境：本地/CI/测试/生产的差异是否影响结论？运行版本、配置名、数据库迁移顺序是否明确？
- 发布：具体产物、部署命令、责任人、授权和观察窗口是什么？无需部署的脚本注明交付入口。
- 冒烟：使用哪个真实用户路径判断上线正常？观察日志/错误率/数据一致性中的哪些信号？
- 恢复：什么条件触发回退？恢复哪个已知可用版本/备份？数据迁移是否能逆转，不能时如何前向修复？
- 凭证：只交接配置名称和取得方式，不把值写入文档、仓库和报告。

不要照搬原资料的服务器规格、固定 CI 产品、Docker 网络或数据库管理员账号。先复用项目已有流水线。自动检查可以随提交运行；部署需要对应任务授权，不能从“测试通过”推导“可以发版”。

## 交接至少回答八个问题

1. 用户原始诉求是什么，本次落实了哪些 AC？
2. 实际改了哪些文件，哪些旧路径被间接影响？
3. 为什么这样设计，拒绝了什么替代方案？
4. 哪些测试在哪个环境/版本运行，证据在哪里？
5. 哪些只在 mock/本地通过，接手者必须复跑什么？
6. 目前阻塞、未验证项、已接受限制分别是什么？
7. 出现问题如何恢复，恢复有什么数据限制？
8. 接下来做什么，谁负责，完成标准是什么？

先填写 .sop/docs/handover.md，再执行 handover。机器快照保留源码指纹、检查结果以及该说明的路径/哈希；工具不会替你推断设计理由。快照 ready 只指材料/登记证据，另看 handover_complete。

接手者先读需求与决定，再核对源码/配置和报告的新鲜度。环境不同需复跑对应集成、UI、数据库/外部服务检查；不要把上个 Agent 的“已通过”当作当前环境实测。

## 失败、未完成也可交接

允许交接部分成果，但逐项标为已实现、已验证、待验证、阻塞。提供复现命令及最后一次失败证据，不能把阻塞列表清空后宣布交付。

记录简短复盘：本次返工来自需求/接口/环境/实现哪一类；新增了什么可复用回归；哪个文档没有帮助决策可以精简。只有可泛化且有证据的经验才加入规则。
