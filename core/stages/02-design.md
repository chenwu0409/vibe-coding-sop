# L2：让需求变成稳定的模块、数据和接口

输入：已明确的需求/AC、宪法、调研结论与现有代码。产出：design.md，high 项目同时填 risk.md。S 项目可把下述适用内容写进 plan 的代码落点与风险部分。

## 设计顺序

1. 画最小系统边界：用户/调用者 → 应用/模块 → 数据/外部依赖。简单 CLI 用文字即可；服务系统画运行单元及调用方向，不为模板添加微服务。
2. 以核心用户路径走一遍调用顺序，识别需要决定的模块边界、事务边界、失败边界。每个模块写职责、对外接口、隐藏的复杂度及调用者。
3. 先定可测试契约：输入类型与约束、成功输出、错误分类、权限、副作用、幂等/重试语义和兼容性。已有 OpenAPI、类型定义或协议文件作为字段唯一来源。
4. 有持久化才设计实体与关系，确认业务唯一性、必填字段、状态转换、删除/保留策略、索引对应查询、并发一致性、迁移和恢复。
5. 逐个外部依赖核对真实文档及版本；明确鉴权配置名（无密钥值）、限流、超时、可重试条件、降级和契约测试。外部行为不由 AI 凭印象补齐。
6. 由实际风险选择权限、数据保护、性能、日志/指标、告警和测试方法；给每项 NFR 配一个验证位置。
7. 高成本/难逆转决定写 ADR：背景、候选、决定和后果。其他局部选择说明理由即可。

## 深模块的判定

调用者是否必须了解内部表结构、重试顺序、缓存细节才能正确调用？如果需要，把稳定行为封装进模块。接口少不等于模块深，避免把所有逻辑塞进一个“万能执行”入口。

例：TaskStore 提供 add/list/complete，调用方不拼接 SQL，也不负责提交事务。CLI 负责参数和用户错误信息，存储层负责持久化与状态更新。接口既能被 CLI 调用，也能由测试直接验证。

## 契约示例

| 接口 | 输入 | 输出/错误 | 副作用与边界 |
|---|---|---|---|
| add(title) | 字符串，去首尾空白后 1–120 字符 | 任务对象；非法标题 ValueError | 成功恰好新增 1 行；失败不写入 |
| complete(id) | 正整数 ID | 更新后的任务；不存在 KeyError | pending→done；done→done 幂等 |
| list_tasks() | 无 | 按 ID 递增的任务列表 | 只读，空库返回空列表 |

这些数字是示例产品已决定的规则，不是所有项目的默认值。

## 数据与外部依赖检查

- 写路径：操作是否需要事务？失败后是否出现部分写入？业务唯一性是否由实际存储机制保证？
- 状态：允许和禁止的迁移分别是什么？重复请求、乱序事件和并发会怎样？
- 迁移：旧数据能否读取？新增字段默认值合理吗？恢复数据库与回退应用是否兼容？
- 外部请求：超时后是否可能已产生副作用？能否安全重试？“所有 4xx 不重试”过于粗糙，应按接口契约区分限流、认证和业务错误。
- 日志：能定位一次失败而不泄露正文、凭证或其他敏感字段吗？

原文的统一软删除、枚举字典表、强制熔断、固定技术栈是场景策略，应结合当前项目选择并验证，不作为通用强制项。

## 完成标准

用所有 P0 AC 走查设计，每项都有承载模块与验证方法。数据/共享接口变化已取得所需决定；未知外部契约已实验或明确标为未验证，不能把 mock 成功描述为真实集成成功。

例外记录影响与替代验证。若当前设计违反宪法，先换方案或修订约束，不能把冲突留给编码 Agent 猜。
