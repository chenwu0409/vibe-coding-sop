# L3：把设计转为能自主执行的工作包

输入：需求、设计、代码现状和测试基线。产出：plan.md；M/L 的 development.md；并行时 tasks.md，影响面复杂时 regression.md。

## Plan：先让一个用户结果成立

1. 选择 QS-001 最小端到端闭环，覆盖真实入口、核心逻辑和必要依赖。例：CLI 创建任务→退出→重新启动→列表看到任务。
2. 写明准备命令、运行命令、输入、预期输出和清理步骤。使用独立测试数据，不能让接手者猜环境变量。
3. 拆出实现顺序：先验证风险最高的依赖/数据假设，再交付第一个切片，然后扩展异常和其他故事。每步关联 AC、改动位置、验证和完成证据。
4. 对每条 C 约束写符合证据或冲突。冲突须有负责人的修订/例外决定，不能只勾“符合”。
5. 扫描直接改动、调用方、共享数据、配置及对外契约，记录要保持的旧行为和对应回归测试。
6. 记录阻塞、责任人、替代路径和阶段交付。不要把尚未取得的凭证、审批或外部能力当作必然可用。

## Development：给出代码落点，保留实现空间

本文件按项目/子系统维护，供多个功能复用。每个功能变化时更新涉及部分：
- 功能→现有/拟建文件、层次、调用方向、AC；
- UI 页面与组件、原型和设计系统位置；无 UI 明确不适用；
- SQL/迁移路径、执行顺序、兼容性和恢复方式；DDL 本体只在迁移文件维护；
- 内部 API 的契约文件/类型路径、鉴权和错误映射；外部 API 引用 design 的契约及版本；
- 关键状态、不变量、默认值和边界；测试用例放测试代码或 validation 映射，避免重复拷贝。

“修改 service，完成接口”不够。应写到“在 task_store.py 的 complete 修改状态更新；cli.py 将 KeyError 转为退出码 2；test_tasks.py 验证不存在与重复完成”。不要把每一行实现预先写进开发文档。

## 并行任务卡

仅在确实需要并行时启用 tasks。每卡包含：
任务 ID、目标与 AC、输入材料、依赖、允许改动文件、共享契约、验证命令、输出、阻塞和接手人。

[P] 的条件是依赖已满足、接口已约定且写入范围不重叠。前端和后端可按同一契约并行，但集成测试必须等两边完成。子任务完成后主执行者必须验证组合行为，不能只汇总“都通过”。

任务粒度以能独立验证和交接为准，原文的 1–3 天、30 分钟不是所有任务的硬限制。

## Agent 任务包示例

“实现 US-001 / AC-001、AC-002。读取 requirements、design 的 add 契约和 development。允许修改 task_store.py、tests/test_tasks.py；CLI 暂不修改。使用临时 SQLite，先覆盖空白标题不写库，再实现合法创建；测试命令见 project.json。交付变更、实际测试输出和未验证项。无需重复确认已约定接口。”

## 开始编码前的检查

- QS-001 是否能由另一个人按命令执行？依赖和数据准备是否齐全？
- 每个本次 AC 是否有任务归属和验证方式？是否出现“写完全部后再想怎么测试”？
- 影响面中每个重要旧路径是否有回归办法？是否能先在旧代码上确认基线？
- Agent 是否有足够的文件定位和授权边界？未决事项是否真正阻塞本任务？

若问题只影响某个任务，先继续其他独立任务。若影响共享契约，回到 L2 决定后再并行。
