# L0：把稳定边界写成可判定的项目约束

输入：用户目标、已有仓库/环境、已经决定的技术和业务边界。产出：constitution.md。对应原 SOP 项目宪法、Approval #1 和 AI 编码规范。

## 执行

1. 用“为谁，在什么场景，解决什么问题”定义项目；产品成功指标留在需求文档。
2. 盘点现有语言/框架/包管理器、运行终端、部署位置、数据边界。写明已知事实的来源；未知选型先列候选与理由，不把猜测写成强制约束。
3. 给稳定约束编号 C-001 等。每条写 MUST/MUST NOT、理由、验证方式。只收纳会改变后续方案的规则；原文 10–30 条是上限启发，不为凑数增加规则。
4. 写“不做什么”。至少明确此次产品边界，防止 Agent 自行添加账号、云同步、后台或复杂架构。
5. 列出 AI 可自主执行范围和负责人需决定的事项。已批准的技术选择、迁移方案和实施任务可直接执行；新商业承诺、未经授权的生产数据操作不能由模板授予权限。
6. 约束有变化时写短 ADR：状态、背景、决定、后果，注明替代的旧决定。实现细节放 design/development，不在宪法重复。

## 例子与反例

可执行条款：
- C-001：任务数据 MUST 保存在用户指定的本地 SQLite 文件；理由是离线使用；验证为重启后任务仍可读。
- C-002：首版 MUST NOT 提供云同步；理由是范围限制；审查网络依赖和验收范围。
- C-003：测试 MUST 使用临时库；理由是隔离用户数据；核对测试路径与清理。

“架构要先进”“注意安全”无法判断符合与否。把它们改为实际需要保护的行为，例如“错误日志不记录用户任务正文”，并安排对应验证。

## 负责人复核

- 目标、约束和不做的范围是否一致？是否把尚未决定的选型冒充已批准？
- 哪一条来自现有系统，哪一条是本次新决定？负责人能否解释每条存在的理由？
- AI 是否知道什么可以自主完成，什么变更超出当前授权？
- 若有例外，是否记录了范围、原因、负责人和重新评估时点？

不存在外部服务、持久化或发布流程时明确不适用及原因。不要套用示例项目的数据库、接口风格、品牌或部署方式。
